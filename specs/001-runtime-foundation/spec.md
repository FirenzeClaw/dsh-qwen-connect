# Feature Specification: 运行时地基重构

**Feature Branch**: `001-runtime-foundation`

**Created**: 2026-11-16

**Status**: 实现中（FR-012 / FR-013 / FR-014 已完成，对应 SC-008 / SC-009 已验证）

**Input**: User description: "均深入"（对 2026-11-16 架构审查报告 7 个候选中属于「地基」阶段的 4 项：构建产物出库、删掉没有消费者的契约层、重试只留一个主人、运行时状态跟着 apply 走）

## 背景

插件当前把运行时状态放在模块级变量里，重试分散在两层，凭据接缝暴露了比实际需要更宽的接口，构建产物被提交进版本库。四项各自独立可验证，但在实现顺序上有依赖：前三项都让「需要被实例化的状态面」变小，第四项在更小的面上动刀。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次上游故障不会让对话等十几分钟 (Priority: P1)

用户发出一条消息，上游在高峰期排队不响应。今天这种情况下界面会持续转圈，最坏约 15 分钟才有结果；用户只能强制刷新，且不知道是网络问题还是插件坏了。

**Why this priority**: 这是唯一直接影响日常使用的问题，且用户已经反馈过「一直转圈」。修复它不需要其他三项。

**Independent Test**: 构造一个永不响应的上游，发出一次请求，测量从发起到收到明确错误的时间；并统计上游实际收到的请求次数。

**Acceptance Scenarios**:

1. **Given** 上游接受了连接但 180 秒内不返回响应头，**When** 用户发出一条消息，**Then** 用户在 3 分钟内看到明确的错误提示，而不是继续转圈。
2. **Given** 上游对首次请求返回 429，**When** 插件向上游发起请求，**Then** 上游收到的请求次数由上层退避策略决定，插件自身不再叠加一层重试。
3. **Given** 上游返回 400，**When** 插件向上游发起请求，**Then** 立即返回该错误，不重试。
4. **Given** 上游返回空回复（`finish_reason` 到达但没有任何内容），**When** 请求结束，**Then** 该次请求被判定为可重试失败，而不是静默结束一轮对话。

---

### User Story 2 - 改配置或禁用插件后，旧状态不会残留 (Priority: P2)

维护者在插件页面上改一次配置（例如模型白名单），或在运行期禁用它。今天这次修改会让插件重新执行一次装配，但上一轮的模型目录、配置快照、适配器句柄都还留在模块级变量里；禁用之后，一个监听本机端口的服务与它的密钥仍然存活。

**Why this priority**: 它决定了改配置是否可信。用户看到「改配置不需要重启」的宣传，但如果新配置与残留的旧状态混合，行为会变得不可预测。

**Independent Test**: 在同一个进程里连续装配两次，各自使用不同配置，检查第一次的配置快照与模型目录不会被第二次读到，也不会反过来污染第二次；再检查装配返回的释放函数被调用后，不再有任何句柄可以触发模型目录广播。

**Acceptance Scenarios**:

1. **Given** 第一次装配的白名单是 A，**When** 用白名单 B 装配第二次，**Then** 第二次读到的配置与模型目录都只反映 B。
2. **Given** 一个已装配的实例，**When** 调用它返回的释放函数，**Then** 适配器注册被撤销，且此后再触发目录刷新不会广播任何事件。
3. **Given** 释放函数已被调用一次，**When** 再次调用它，**Then** 不抛错，且释放动作不会重复发生。
4. **Given** 从未装配过任何实例，**When** 读取「生效配置」，**Then** 返回默认值而不是抛错（排障入口必须始终可读）。

---

### User Story 3 - 账号查询只发生一次 (Priority: P3)

排障时需要同时看账号、套餐、积分。今天调用链会为此发起三次完整的账号查询，得到的是同一份数据的三个切片；三个接口的名字还暗示它们是三次独立查询。

**Why this priority**: 它降低排障成本与上游压力，但不影响正常对话。

**Independent Test**: 依次取账号、套餐、积分，统计上游被请求的次数。

**Acceptance Scenarios**:

1. **Given** 凭据有效，**When** 取一次账号概览，**Then** 上游只收到一次账号查询，且返回结果同时包含账号、套餐、积分三部分。
2. **Given** 凭据模块加载失败，**When** 请求任何账号信息，**Then** 抛出带有可执行恢复建议的错误，而不是返回空对象。
3. **Given** 凭据模块文件存在但内容损坏，**When** 请求账号信息，**Then** 错误信息指向真实原因（文件损坏），而不是指向一个不存在的备选路径。

---

### User Story 4 - 克隆仓库后搜到的就是当前代码 (Priority: P4)

维护者或 AI 助手克隆仓库后用文本搜索找某个函数。今天有 87% 的受跟踪文件是构建产物，其中三份核心文件已经与源码不同，于是同一个函数名会命中多处，其中一处是过时的。

**Why this priority**: 它不影响运行时行为，但持续制造误判；且越早做，后面三项的 diff 越干净。

**Independent Test**: 检查版本库里是否还跟踪构建产物目录；在没有构建产物的情况下跑一次全量验证，确认验证工具不会因此报失败。

**Acceptance Scenarios**:

1. **Given** 一个刚克隆的仓库，**When** 搜索一个只在源码里定义一次的函数名，**Then** 只命中一处定义。
2. **Given** 一个刚克隆、尚未构建的仓库，**When** 跑全量验证，**Then** 构建产物相关的检查被明确标记为「跳过」并给出生成方法，而不是判定失败。
3. **Given** 工作区里存在构建产物，**When** 从版本库移除它们的跟踪，**Then** 工作区文件保持不变，后续的本地安装与打包仍可使用它们。

---

### Edge Cases

- 上游在返回响应头之后、首个内容帧之前卡住：必须给下游明确的错误帧，而不是让连接静默关闭（否则下游看到「正常结束但无内容」）。
- 上游在流中途报错：不得再补一个「正常结束」帧，否则真实原因被通用错误覆盖。
- 上游给出结束帧但尚未给出用量统计：继续读到流结束，以取得随后到达的用量帧。
- 客户端在流进行中断开：及时中断上游，且之后不再向上游写任何东西。
- 插件在配置校验失败时被装配：装配不得抛异常（否则宿主显示红色错误横幅），应记录日志并保持模型可见。
- 两个实例同时存在时释放其中一个：另一个必须仍可正常读取配置与刷新目录。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 对上游超时只等待一次，不得在同一层重复尝试同一超时请求。
- **FR-002**: 系统 MUST 把「可重试失败」的判定收敛到单一一层，使一次用户请求产生的上游请求次数有确定上界。
- **FR-003**: 系统 MUST 保留对限流（429）与服务端瞬时故障（5xx）的退避重试，且退避策略只存在一套。
- **FR-004**: 系统 MUST 把空回复视为可重试失败，而不是正常完成。
- **FR-005**: 系统 MUST 让每次装配持有自己的一份配置快照、模型目录与适配器注册，装配之间互不可见。
- **FR-006**: 系统 MUST 在装配返回的释放函数被调用后撤销适配器注册，并使后续目录刷新不再广播。
- **FR-007**: 释放函数 MUST 幂等：重复调用不抛错、不重复释放。
- **FR-008**: 系统 MUST 在从未装配时仍能读出默认的生效配置（排障入口始终可用）。
- **FR-009**: 系统 MUST 让账号、套餐、积分三项信息来自同一次查询。
- **FR-010**: 系统 MUST 在凭据模块缺失或损坏时给出指向真实原因的错误与恢复建议。
- **FR-011**: 凭据接缝 MUST 只暴露调用方真正使用的入口，实现细节（模块加载器）不作为公开接口。
- **FR-012**: 版本库 MUST NOT 跟踪构建产物目录；工作区中的对应文件 MUST 保留。
- **FR-013**: 全量验证 MUST 在构建产物缺失时标记跳过并给出生成方法，而不是失败。
- **FR-014**: 系统 MUST 提供一个可执行检查，断言构建产物未被版本库跟踪。

### Key Entities

- **装配实例（Runtime）**：一次装配产生的整体，持有该次的配置快照、模型目录、适配器注册与释放函数。实例之间不共享可变状态。
- **生效配置快照**：用户配置经校验后、供卡片与排障入口读取的脱敏副本。始终是副本，外部修改不影响实例。
- **模型目录**：当前可选模型的集合及其来源标识（内置 / 上游 / 上游但白名单为空而降级）。
- **可重试失败**：可以被重复尝试的失败分类，包含限流、服务端瞬时故障、传输中断、空回复；不包含超时与请求非法。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上游超时场景下，用户从发消息到看到明确错误的等待时间从最坏约 15 分钟降到不超过 3 分钟。
- **SC-002**: 一次用户请求产生的上游请求次数有确定上界，且该上界由单一一层决定（不再出现两层相乘）。
- **SC-003**: 空回复场景从「静默结束一轮对话」变为「自动重试后给出结果或明确错误」，覆盖率为 100%（今天为 0%）。
- **SC-004**: 连续两次不同配置的装配之间，配置与模型目录的相互污染为 0 项（可断言）。
- **SC-005**: 插件被禁用后，其占用的本机监听端点数为 0（今天为 1）。
- **SC-006**: 取账号、套餐、积分三项信息所需的上游查询次数从 3 次降到 1 次。
- **SC-007**: 凭据接缝的公开入口数从 8 个降到 5 个。
- **SC-008**: 版本库受跟踪文件数从 2398 个降到 300 个以内，其中构建产物数为 0。
- **SC-009**: 在无构建产物的全新克隆上，全量验证通过且失败项为 0。

## Assumptions

- 宿主框架在配置变更时会重新执行装配，并调用上一次装配登记的释放函数；这一行为已在当前宿主版本实测确认。
- 宿主框架自带的重试机制在插件所在 profile 中默认启用，且对限流与服务端瞬时故障生效。
- 千问上游的账号查询接口一次返回账号、套餐、积分三部分，无需额外请求。
- 构建产物可由仓库内的打包工具随时重新生成，不存在只能从版本库取回的内容。
- 本机监听端点只绑定环回地址、且要求进程内共享密钥，因此「随进程退出」而非「随禁用关闭」是可接受的取舍（已在设计阶段确认）。
