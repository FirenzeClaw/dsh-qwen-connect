# Feature Specification: 流式转写与检查工具收敛

**Feature Branch**: `003-stream-and-tools`

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "均深入"（对 2026-11-16 架构审查报告候选 4 与候选 5：把流式转写从 HTTP 处理函数里拆出来；客户端的加载器只写一份）

## 背景

两项都是「同一段逻辑出现在错误的地方」：一项是十份流状态与 HTTP 关注点挤在同一个函数里，导致纯行为必须跨网络才能验证；另一项是同一段浏览器装载逻辑被抄了三份，其中一份还因为写死了开发机路径而长期静默跳过。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 流式帧的行为可以不起网络就能验证 (Priority: P1)

维护者要改「上游在结束帧之后才给出用量统计」这类行为。今天验证它必须同时起一个假上游和一个本地代理，两边的时序都要照顾，写一条测试的成本远高于改一行代码。

**Why this priority**: 流的边界情况是这个插件最容易出错的地方（中断、空回复、中途报错、静默卡死），而当前验证成本高到足以让人跳过验证。

**Independent Test**: 把上游字节序列直接喂给转写组件，检查产出的帧序列；全程不监听任何端口。

**Acceptance Scenarios**:

1. **Given** 上游字节里包含一段正文，**When** 把字节喂给转写组件，**Then** 产出的帧包含该正文，且带有正确的模型标识与序号。
2. **Given** 上游先给结束帧、再单独给一帧用量统计，**When** 把字节喂完，**Then** 用量统计出现在最后一个帧上，且不会出现第二个结束帧。
3. **Given** 上游在流中途报告错误，**When** 转写结束，**Then** 产出错误帧与终止标记，且**不**产出「正常结束」帧。
4. **Given** 上游在超时窗口内没有产生任何帧，**When** 看门狗触发，**Then** 先产出一个明确的错误帧再终止，而不是静默关闭。
5. **Given** 客户端在流进行中已经断开，**When** 继续喂入剩余字节，**Then** 不再产出任何帧。

---

### User Story 2 - 客户端检查工具不再重复实现装载逻辑 (Priority: P2)

维护者要新增一项客户端检查（例如某个新槽位的渲染）。今天需要在三个已有工具里挑一个复制装载段、React 桩与上下文桩，再改断言；这三份桩彼此不同，复制时会引入哪一份的隐含假设并不明显。

**Why this priority**: 它降低新增检查的成本，并消除「一份工具长期静默跳过」这类问题的复发条件。

**Independent Test**: 在共享装载模块存在的前提下新增一项检查，确认只需编写断言即可运行，且无需复制装载代码。

**Acceptance Scenarios**:

1. **Given** 共享装载模块存在，**When** 运行任意一个客户端检查，**Then** 三者使用同一份装载逻辑与同一套上下文桩。
2. **Given** 运行环境里没有安装可选渲染依赖，**When** 运行需要渲染的检查，**Then** 该检查以「跳过」退出码结束并给出安装指引，而不是判定失败。
3. **Given** 运行环境里没有安装可选渲染依赖，**When** 运行不需要渲染的模块加载检查，**Then** 该检查**仍然正常执行并给出结论**（不得因缺少可选依赖而跳过）。
4. **Given** 某个检查工具的代码里出现开发机专属的绝对路径字面量，**When** 运行全量验证，**Then** 该情况被明确拦下。

---

### Edge Cases

- 上游字节在 UTF-8 多字节字符中间被切断：转写必须跨块正确拼接，不得产出替换字符。
- 上游发送畸形帧（非 JSON、空帧、注释行）：跳过并计数，不得中断整个流。
- 上游发送终止哨兵后再发内容：以终止哨兵为准，忽略后续。
- 转写组件被重复终止：终止操作必须幂等，不重复写终止标记。
- 客户端断开与看门狗同时触发：只产出一份错误帧与一个终止标记。
- 检查工具在装载阶段就抛异常：必须以失败退出（而不是静默跳过），并输出可定位的堆栈。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 把「上游字节 → 下游帧」的转写与 HTTP 请求处理分离为两个可独立调用的单元。
- **FR-002**: 转写单元 MUST 不使用任何 HTTP 请求/响应对象，帧的输出通过调用方提供的回调。
- **FR-003**: 转写单元 MUST 自己持有全部流状态（是否已结束、是否出错、用量统计、首内容时刻、输出长度、看门狗是否触发）。
- **FR-004**: HTTP 连接生命周期（客户端是否断开）与上游传输中断控制 MUST 留在请求处理侧，不进转写单元。
- **FR-005**: 转写单元 MUST 在出错后不产出「正常结束」帧。
- **FR-006**: 转写单元 MUST 在超时看门狗触发时先产出错误帧再终止。
- **FR-007**: 转写单元 MUST 在收到结束帧但尚无用量统计时继续接收，以取得随后到达的用量。
- **FR-008**: 转写单元 MUST 幂等终止，且终止后不再产出帧。
- **FR-009**: 三个客户端检查工具 MUST 共用同一份「装载客户端模块 + 上下文桩 + 文案字典」的实现。
- **FR-010**: 共享装载实现 MUST 允许调用方传入自定义的渲染库实现，使不需要渲染的检查可以零依赖运行。
- **FR-011**: 可选的渲染依赖缺失时，需要渲染的检查 MUST 以统一的「跳过」退出码结束并给出安装指引。
- **FR-012**: 全量验证 MUST 在检查工具含开发机专属路径字面量时判定失败。

### Key Entities

- **转写单元（Stream Relay）**：接收上游字节序列，产出下游帧序列。持有全部流状态，不知道 HTTP 存在。
- **帧（Frame）**：发给下游的一个数据块，可能是正文增量、结束标记、用量统计或错误。
- **流状态**：一组描述「这次流转写进行到哪一步」的事实，包括是否已结束、是否出错、是否超时、累计输出长度。
- **共享装载实现（Client Harness）**：把客户端模块在受控环境里装载并执行，记录其注册结果，供各检查工具断言。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 涉及流式帧行为的验证中，需要监听网络端口的比例从接近 100% 降到 30% 以下。
- **SC-002**: 请求处理函数从约 376 行降到 120 行以内，且剩余的每一行都属于请求/响应职责。
- **SC-003**: 三个客户端检查工具的装载代码从 3 份降到 1 份，重复行数减少约 250 行。
- **SC-004**: 「无需渲染的检查」在未安装可选依赖的环境下仍能执行的比例为 100%。
- **SC-005**: 检查工具中出现开发机专属绝对路径的情况被全量验证拦下的覆盖率为 100%。

## Assumptions

- 下游协议期望的是 OpenAI 兼容的分块流格式，转写单元的产出必须符合该格式（既有行为，不变）。
- 上游的用量统计可能迟到，因此转写单元必须能接受「结束帧之后再收帧」。
- 三个客户端检查中，只有「模块加载契约」一项被设计为在零可选依赖下运行；另两项需要真实渲染库。
- 可选的渲染依赖属于开发期工具依赖，不进入插件的运行时依赖清单。
