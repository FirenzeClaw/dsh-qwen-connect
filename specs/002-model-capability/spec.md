# Feature Specification: 模型能力收成单一判据

**Feature Branch**: `002-model-capability`

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "均深入"（对 2026-11-16 架构审查报告候选 1：把「模型能做什么」收成一个 interface）

## 背景

「这个模型能做什么」今天有六个住处，其中两处没有数据可查、只能写死。这已经造成过一次真实缺陷（设置卡片写「仅文本」，而模型选择器实际声明支持图片）；还有一处是结构欠账（请求体里的「是否会思考」恒为真，因为模型形状里根本没有这个字段可查）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 卡片文案与实际能力永远一致 (Priority: P1)

用户在插件页面看到模型的描述，读完决定用不用它。今天这个描述与实际行为可能矛盾：卡片说只支持文本，而选择器允许附图片。

**Why this priority**: 这是已经发生过的一次真实缺陷，用户直接看到矛盾信息。

**Independent Test**: 在「模型声明支持图片 × 本机能否投递图片」的全部四种组合下，比对设置卡片文案与模型声明给宿主的能力，要求逐项一致。

**Acceptance Scenarios**:

1. **Given** 模型声明支持图片且本机附件服务可用，**When** 读取卡片文案与模型能力声明，**Then** 两者都表示「文本+图片」。
2. **Given** 模型声明支持图片但本机附件服务不可用，**When** 读取卡片文案与模型能力声明，**Then** 两者都表示「仅文本」，且模型不声明图片输入。
3. **Given** 模型未声明支持图片，**When** 读取卡片文案与模型能力声明，**Then** 两者都表示「仅文本」，与附件服务是否可用无关。
4. **Given** 上游目录新增一个本机内置目录里没有的模型，**When** 打开选择器与卡片，**Then** 两处的图片能力判断都来自该模型的上游声明，而不是内置目录的默认值。

---

### User Story 2 - 关闭思考后请求真的不带思考 (Priority: P2)

用户关掉了「允许模型思考」。今天这个开关只影响呈现给用户的选择器，请求体里另有一处「是否会思考」的标记恒为真。

**Why this priority**: 用户关掉一个开关却还在付思考的钱，属于静默违背用户意图。今天恰好没有暴露，因为上游所有模型都声明会思考；一旦上游差异化就会暴露。

**Independent Test**: 在「模型声明会思考 / 不会思考」两种情况下，分别开启与关闭思考总开关，检查发往上游的请求体里的思考相关字段。

**Acceptance Scenarios**:

1. **Given** 思考总开关开启且模型声明会思考，**When** 发出请求，**Then** 请求体声明该模型会思考，并带上用户选择的思考深度。
2. **Given** 思考总开关关闭，**When** 发出请求，**Then** 请求体在三个相关字段上都表示「不思考」，且不残留上一次的思考深度。
3. **Given** 模型在上游声明为不会思考，**When** 发出请求，**Then** 请求体不声明该模型会思考，且不提供任何思考深度选项。
4. **Given** 上游目录里某个模型的「是否会思考」从真变为假，**When** 插件重新拉取目录，**Then** 该模型的能力判断随之改变，无需修改代码。

---

### User Story 3 - 思考档位清单不再需要人工同步 (Priority: P3)

上游新增一个思考档位，或维护者想调整可以提供的档位。今天客户端的档位清单是手抄的一份常量，与权威清单可能不一致：权威加了一档而表单漏掉，界面上就永久少一个开关，且没有任何报错。

**Why this priority**: 它是维护性收益，不影响当前正确性（已有一道回归网守着漂移）。

**Independent Test**: 在权威档位清单里新增一个档位，检查设置表单是否自动多出对应开关，且不需要改客户端代码。

**Acceptance Scenarios**:

1. **Given** 权威档位清单包含五个档位，**When** 打开设置表单，**Then** 五档各有一个独立开关。
2. **Given** 权威档位清单新增第六档，**When** 打开设置表单，**Then** 第六档的开关自动出现，客户端代码未改动。
3. **Given** 权威档位清单为空（全部关闭），**When** 查看模型能力声明，**Then** 不声明任何思考档位（而不是声明一个空列表）。

---

### Edge Cases

- 上游目录里完全没有某个模型：请求该模型必须给出明确错误，不得退化成「按不支持图片处理」而继续发请求。
- 上游未声明思考档位（当前所有模型都是这种情况）：必须按经验值提供实测可用的档位，并在代码注释里写明这是经验值而非上游保证。
- 上游把某个档位声明为不可用：该档位不得出现在选择器里。
- 上游目录里某个模型被标记为停用：不纳入能力目录。
- 同一个能力被两处消费（卡片与请求体）时，其中一处的入参缺失：必须回退到模型声明，而不是回退到「不支持」。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 把「模型声明什么」与「本机能否投递」作为两个独立事实分别记录，最终结论由两者共同决定。
- **FR-002**: 系统 MUST 让设置卡片文案与模型能力声明来自同一个判据，两者不得各自判断。
- **FR-003**: 系统 MUST 从上游目录读取「模型是否会思考」，不得写死。
- **FR-004**: 系统 MUST 让「不思考」在请求体的所有相关字段上一致表达，不得只改其中一处。
- **FR-005**: 系统 MUST 从上游目录读取「模型是否支持图片」，不得回退到内置目录的默认值。
- **FR-006**: 系统 MUST 在思考档位全部关闭时不声明任何档位，而不是声明空列表。
- **FR-007**: 系统 MUST 让可提供的思考档位由「配置启用 ∩ 模型可用」决定。
- **FR-008**: 设置表单 MUST 从权威配置数据派生档位开关清单，不得维护一份手抄常量。
- **FR-009**: 系统 MUST 在上游未声明思考档位时使用标注为「经验值」的档位集合。
- **FR-010**: 系统 MUST 在请求一个不在能力目录里的模型时给出明确错误。

### Key Entities

- **能力（Capability）**：关于一个模型的一组判断，包含能否传图、是否会思考、可用思考档位。每一项都由「模型声明」与「本机投递能力」两个来源合成。
- **模型声明**：来自上游目录的原始事实（是否支持图片、是否会思考、上下文档位）。
- **投递画像（Delivery Profile）**：本机所处环境的事实（附件服务是否可用、哪些思考档位被配置启用）。
- **最终结论**：卡片文案、模型能力声明、请求体字段三处共同读取的那一个值。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 卡片文案与模型能力声明在四种「声明 × 投递」组合下的不一致项为 0。
- **SC-002**: 发往上游的请求体中，「不思考」在三个相关字段上的一致表达率为 100%。
- **SC-003**: 上游把某个模型改为「不会思考」后，插件无需改代码即可正确反映，验证通过。
- **SC-004**: 权威档位清单新增一档后，设置表单自动出现该开关，客户端改动行数为 0。
- **SC-005**: 判断「模型能做什么」的代码位置从 6 处收敛到 1 处。

## Assumptions

- 上游模型目录接口会返回「是否支持图片」与「是否会思考」两个布尔字段；当前 13 个模型的取值全部为真，因此这两个判据今天没有区分度，但结构上必须支持差异化。
- 上游目录当前不声明思考档位（全部为 null），因此档位集合来自实测经验值；这属于已知的、已在注释中标注的不确定性。
- 用户配置的思考档位启用状态与模型自身可用的档位是两类独立约束，取交集。
- 本机附件服务是否存在由宿主上下文决定，插件只能观测不能改变。
